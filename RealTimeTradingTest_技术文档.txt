================================================================================
一、系统概述
================================================================================

RealTimeTradingTest 是一个基于 SpringBoot 的实时交易策略测试类，
通过 WebSocket 连接币安(Binance)获取 ETH/USDT 1秒K线实时数据，
并行执行多个策略版本，自动开单、结算、记录日志。

核心流程:
  1. 启动时检查数据库K线数据连续性，补全缺失数据
  2. 连接币安 WebSocket (wss://data-stream.binance.vision/ws/ethusdt@kline_1s)
  3. 实时接收1秒K线数据，存入内存缓冲池 (ConcurrentSkipListMap)
  4. 在每个K线到达时，按窗口大小分组计算极值
  5. 各策略版本独立判断开单条件，满足则开单并写入数据库
  6. 定时任务每秒检查待结算交易，到期自动结算
  7. 定时任务清理过期数据、打印状态、健康检查
  8. 同时将K线数据批量写入数据库供回测使用

数据源: 币安 WebSocket 1秒K线流
交易对: ETH/USDT
盈亏规则: 方向正确 +4U, 方向错误 -5U, 超时 -5U
数据缓冲: 4小时
运行模式: 持续运行，Ctrl+C 停止

2.1 依赖注入 (Spring Beans)
    - IEthTradeRecordService  tradeRecordService   交易记录服务
    - IEthKlineSecondService  ethKlineSecondService  K线数据服务

2.2 核心数据结构

    ┌─────────────────────────────────────────────────────────┐
    │  ConcurrentSkipListMap<Long, KlineData> dataBuffer       │
    │  (按时间戳排序的1秒K线缓冲池，线程安全)                     │
    ├─────────────────────────────────────────────────────────┤
    │  ConcurrentHashMap<Long, PendingTrade> pendingTrades     │
    │  (待结算交易队列，key=数据库记录ID)                        │
    ├─────────────────────────────────────────────────────────┤
    │  List<StrategyVersion> versions                          │
    │  (策略版本列表，数据驱动)                                  │
    ├─────────────────────────────────────────────────────────┤
    │  Map<Long, WindowState> winStates                        │
    │  (窗口大小 → 窗口状态映射，管理冷却/去重)                   │
    └─────────────────────────────────────────────────────────┘

2.3 数据模型

    KlineData          - 1秒K线数据 (timestamp, open, close, high, low, volume)
    PendingTrade       - 待结算交易 (dbId, openTs, targetTs, direction, openPrice, strategyVersion)
    ExtremaResult      - 窗口极值结果 (maxData, minData, maxPrice, minPrice, maxTs, minTs)
    StrategyVersion    - 策略版本配置+计数器
    WindowState        - 窗口状态 (冷却时间戳, 去重时间戳)
    KlinePoint         - 回放用K线点
    ReplayTrade        - 回放交易结果
    LossDetail         - 亏损详情 (V3分析)
    LossCluster        - 亏损簇 (连续亏损归组)

三、策略版本系统
================================================================================

3.1 设计理念
    采用数据驱动架构，每个策略版本封装为 StrategyVersion 对象，
    包含配置参数和独立统计计数器。新增版本只需在 initVersions() 中注册一行。

3.2 StrategyVersion 字段

    name              - 版本标识 (如 "base", "v1")
    label             - 显示标签 (如 "base(20m/10m)")
    windowUs          - 窗口大小 (微秒)
    settleUs          - 结算等待时间 (微秒)
    gapUs             - 极值距当前允许的最小时差 (微秒)
    trendThreshold    - 趋势过滤阈值 (0=无过滤, 0.002=0.2%, 0.005=0.5%)

    计数器:
    totalTrades       - 开单总数
    longTrades        - 多单数
    shortTrades       - 空单数
    settledCount      - 已结算数
    winCount          - 盈利数
    loseCount         - 亏损数
    timeoutCount      - 超时数
    skippedByTrend    - 被趋势过滤跳过的次数

3.3 WindowState 字段

    lastTradeTs       - 上次开单时间戳 (冷却控制, 同窗口内间隔≥1分钟)
    lastShortTs       - 上次空单极值时间戳 (去重, 同一极值不重复开单)
    lastLongTs        - 上次多单极值时间戳 (去重)
    firstSatisfied    - 窗口是否首次满足条件 (用于日志)

3.4 当前策略版本列表 (7个版本)

    ┌───────┬──────────────┬──────────┬──────────┬──────────┬──────────┐
    │ 版本  │ 窗口大小     │ 结算时间 │ 极值间隙 │ 趋势过滤 │ 说明     │
    ├───────┼──────────────┼──────────┼──────────┼──────────┼──────────┤
    │ base  │ 20分钟       │ 10分钟   │ 3分钟    │ 无       │ 基准策略 │
    │ v1    │ 20分钟       │ 10分钟   │ 3分钟    │ 0.2%     │ 趋势过滤 │
    │ v2    │ 20分钟       │ 10分钟   │ 3分钟    │ 0.5%     │ 趋势过滤 │
    │ v5    │ 20分钟       │ 30分钟   │ 3分钟    │ 无       │ 延迟结算 │
    │ v3    │ 15分钟       │ 10分钟   │ 1分钟    │ 无       │ 短窗口   │
    │ v4    │ 30分钟       │ 10分钟   │ 1分钟    │ 无       │ 长窗口   │
    │ v6    │ 2小时        │ 1小时    │ 1分钟    │ 无       │ 超长周期 │
    └───────┴──────────────┴──────────┴──────────┴──────────┴──────────┘

    窗口分组 (同窗口共享极值计算):
    - 20分钟窗口: base, v1, v2, v5 (极值共享, 间隙=3分钟)
    - 15分钟窗口: v3
    - 30分钟窗口: v4
    - 2小时窗口:  v6

3.5 扩展新策略
    只需在 initVersions() 中添加一行:
    registerVersion("新名称", "标签", 窗口大小, 结算时间, 极值间隙, 趋势阈值);

    所有统计、面板、报告自动适配。


================================================================================
四、数据流与缓冲
================================================================================

4.1 数据接收流程

    WebSocket (币安) → onMessage → handleKlineMessage()
        │
        ├─ 解析JSON, 提取K线对象
        ├─ 只处理已闭合K线 (kline.x == true)
        ├─ 存入 dataBuffer (ConcurrentSkipListMap, 按时间戳排序)
        ├─ 更新健康状态: lastKlineDataAt, dataHealthy=true, consecutiveMissCount=0
        ├─ 每60条打印数据速率
        ├─ writeKlineToDatabase() 写入缓冲
        └─ executeStrategy() 执行策略

4.2 数据缓冲 (dataBuffer)

    - 类型: ConcurrentSkipListMap<Long, KlineData>
    - 容量: 约4小时数据 (14400条)
    - 清理: 每小时删除4小时前的数据
    - 子窗口查询: dataBuffer.subMap(start, true, end, false)

4.3 时间戳体系

    系统内部统一使用微秒(μs)作为时间戳单位:
    - 币安WebSocket返回毫秒 → ×1000 → 微秒
    - 数据库可能存毫秒或微秒 → 自适应检测

    时间常量:
    ONE_MINUTE_US      = 60,000,000       (1分钟)
    THREE_MINUTES_US   = 180,000,000      (3分钟)
    FIVE_MINUTES_US    = 300,000,000      (5分钟)
    TEN_MINUTES_US     = 600,000,000      (10分钟)
    FIFTEEN_MINUTES_US = 900,000,000      (15分钟)
    TWENTY_MINUTES_US  = 1,200,000,000    (20分钟)
    THIRTY_MINUTES_US  = 1,800,000,000    (30分钟)
    ONE_HOUR_US        = 3,600,000,000    (1小时)
    TWO_HOURS_US       = 7,200,000,000    (2小时)
    FOUR_HOURS_US      = 14,400,000,000   (4小时)


================================================================================
五、核心交易逻辑
================================================================================

5.1 executeStrategy(KlineData currentData)

    每个K线到达时调用，执行流程:

    1. 数据新鲜度检查
       - 如果缓冲最新数据超过90秒未更新 → 跳过策略执行

    2. 按窗口大小分组
       - 遍历所有策略版本，按 windowUs 去重
       - 同一窗口大小只计算一次极值 (共享)

    3. 计算窗口极值 (findExtrema)
       - 窗口: [currentTs - windowUs, currentTs)
       - 要求窗口内数据覆盖至少 windowUs - 1分钟
       - 找到最高价(close)和最低价(close)的K线

    4. 处理该窗口下的所有版本 (processVersion)
       - 遍历同窗口的所有策略版本
       - 每个版本独立判断开单条件

    5. 诊断日志 (每60次调用)
       - 打印各窗口的gap值 (极值距当前时间)
       - 用于调试和监控

5.2 findExtrema(currentTs, currentPrice, windowUs, minWindowUs, ws)

    在指定窗口内寻找最高价和最低价:

    步骤:
      1. 截取窗口数据: dataBuffer.subMap(currentTs-windowUs, currentTs)
      2. 检查窗口覆盖: 数据时长 ≥ minWindowUs (windowUs - 1分钟)
      3. 首次满足时打印日志 (通过 WindowState.firstSatisfied)
      4. 遍历窗口内所有K线，找最高价和最低价
      5. 返回 ExtremaResult (maxData, minData, maxTs, minTs)

    注意: 使用 close 价格 (非 high/low) 作为极值判断依据

5.3 processVersion(currentTs, currentPrice, ext, ver, ws)

    处理单个策略版本的开单逻辑:

    前置条件:
      1. dataHealthy == true (数据健康)
      2. 极值距当前时间 ≥ ver.gapUs (20分钟窗口=3分钟, 其他=1分钟)
      3. 极值时间戳未重复开单 (去重)
      4. 同窗口内上次开单距今 ≥ 1分钟 (冷却)

    空单条件:
      最高价出现 gapUs 后 → 开空单
      如果趋势过滤开启且为上涨趋势 → 跳过

    多单条件:
      最低价出现 gapUs 后 → 开多单
      如果趋势过滤开启且为下跌趋势 → 跳过

    趋势过滤逻辑:
      - isTrendUp: 当前价 vs 5分钟前价格, 涨幅超过阈值 → 上涨
      - isTrendDown: 当前价 vs 5分钟前价格, 跌幅超过阈值 → 下跌
      - 上涨趋势中不开空单, 下跌趋势中不开多单

5.4 createTrade(maxData, minData, direction, openTs, openPrice, ver)

    创建开单记录:

    步骤:
      1. 构建 EthTradeRecord 对象 (含开单时间、方向、价格、极值信息)
      2. 调用 tradeRecordService.createTrade() 写入数据库
      3. 创建 PendingTrade 对象, 加入待结算队列
      4. 计算结算时间: targetTs = openTs + ver.settleUs
      5. 更新对应版本的计数器 (totalTrades, shortTrades/longTrades)
      6. 写入日志


================================================================================
六、结算机制
================================================================================

6.1 checkPendingSettlements()

    由定时任务每秒调用一次，检查待结算交易队列:

    遍历 pendingTrades 中的所有待结算交易:

    情况A: 数据存在 (正常结算)
      1. 使用 floorEntry 容错查找 (允许1秒误差)
      2. 找到了目标时间戳的K线数据
      3. 判断胜负:
         - 多单: 收盘价 > 开单价 → 盈利 (+4U)
         - 空单: 收盘价 < 开单价 → 盈利 (+4U)
         - 否则 → 亏损 (-5U)
      4. 调用 tradeRecordService.settleTrade() 更新数据库
      5. 更新对应版本的计数器 (settledCount, winCount/loseCount)
      6. 重置 consecutiveMissCount = 0

    情况B: 数据缺失且超过5分钟 (超时结算)
      1. 标记为超时, 盈亏 -5U
      2. 更新对应版本的 timeoutCount
      3. consecutiveMissCount++
      4. 如果连续缺失 ≥ 5次 → 标记 dataHealthy = false, 暂停开单

    情况C: 数据缺失但未超时 (等待)
      1. 不做处理, 等待下次检查

6.2 结算容错机制

    使用 floorEntry 替代精确匹配:
    - 目标时间戳的K线可能因WebSocket丢包而缺失
    - floorEntry 返回 ≤ 目标时间戳的最大K线
    - 允许误差 ≤ 1分钟 (ONE_MINUTE_US)
    - 避免因缺秒导致大量超时

6.3 盈亏汇总

    全局盈亏 = 所有版本 calcProfit() 之和
    calcProfit() = wins × 4 - loses × 5 - timeouts × 5

七、定时任务体系
================================================================================

7.1 任务列表 (5个线程池)

    ┌──────────────┬──────────┬──────────────────────────┐
    │ 任务名称     │ 频率     │ 功能                     │
    ├──────────────┼──────────┼──────────────────────────┤
    │ 结算检查     │ 1秒      │ checkPendingSettlements  │
    │ 状态打印     │ 5分钟    │ printStatus              │
    │ 数据清理     │ 1小时    │ cleanupOldData           │
    │ K线刷库      │ 30秒     │ flushKlineBuffer         │
    │ 健康检查     │ 30秒     │ healthCheck              │
    └──────────────┴──────────┴──────────────────────────┘

7.2 任务异常保护

    所有定时任务通过 wrapTask() 包装:
    - 捕获 Throwable 级别异常
    - 打印错误日志
    - 防止任务静默终止

7.3 启动时清理

    cleanupStalePendingTrades():
    - 查询数据库中所有"待结算"记录
    - 创建时间超过4小时的 → 标记为"超时"结算
    - 清理上次运行残留的脏数据

7.4 JVM关闭钩子

    Runtime.addShutdownHook():
    - 设置 running = false
    - 刷新K线缓冲到数据库
    - 打印最终报告
    - 关闭日志文件
    - 释放 shutdownLatch


================================================================================
八、健康监控与容错
================================================================================

8.1 监控指标

    dataHealthy        - 数据是否健康 (控制开单)
    lastRawMessageAt   - 最后收到WebSocket原始消息的时间
    lastKlineDataAt    - 最后成功解析K线数据的时间
    reconnectCount     - WebSocket重连次数
    consecutiveMissCount - 连续结算数据缺失次数

8.2 healthCheck() (每30秒)

    检测逻辑:
      1. 计算静默时间 = now - lastRawMessageAt
      2. 如果静默超过60秒:
         - 标记 dataHealthy = false
         - 主动关闭旧WebSocket连接
         - 等待3秒后尝试重连
         - 重连成功 → 恢复 dataHealthy = true
         - 重连失败 → 记录错误日志

8.3 数据健康对开单的影响

    processVersion() 开头检查:
      if (!dataHealthy) return;  // 数据不健康时暂停开单

    executeStrategy() 开头检查:
      如果缓冲最新数据超过90秒未更新 → 跳过策略执行

8.4 WebSocket 重连机制

    三重重连保障:
      1. @OnClose 回调 → 等待5秒 → 重连
      2. @OnError 回调 → 等待5秒 → 重连
      3. healthCheck() 定时任务 → 检测静默 → 主动重连

    重连后:
      - reconnectCount++
      - dataHealthy 自动恢复 (收到新数据时设置)

================================================================================
十、K线数据持久化
================================================================================

10.1 数据连续性 (ensureDataContinuity)

    启动时调用:
      1. 查询数据库最新K线记录
      2. 自动检测数据库时间戳格式 (毫秒/微秒)
      3. 计算数据滞后时间
      4. 如果滞后超过5秒 → 从币安API补全缺失数据
      5. 按1000条/批次下载, 写入数据库

    用于确保回测数据完整性。

10.2 实时写入缓冲 (writeKlineToDatabase)

    每个K线到达时:
      1. 自适应时间戳格式转换 (毫秒↔微秒)
      2. 去重检查 (writtenTimestamps)
      3. 构造 EthKlineSecond 对象
      4. 加入写入缓冲队列 (klineWriteBuffer)
      5. 缓冲达到500条 → 触发批量刷新

10.3 批量刷新 (flushKlineBuffer)

    触发条件:
      - 定时任务每30秒
      - 缓冲满500条

    操作:
      1. 同步锁保护 (klineFlushLock)
      2. 取出缓冲中所有数据
      3. 调用 ethKlineSecondService.saveBatchKlineData()
      4. 失败时数据回放缓冲

10.4 去重机制

    writtenTimestamps (ConcurrentHashMap.newKeySet()):
    - 记录已写入数据库的时间戳
    - 30分钟过期自动清理
    - 防止重复写入

十二、配置参数速查
================================================================================

12.1 时间参数
    数据缓冲: 4小时
    数据清理: 每小时清理4小时前数据
    K线刷库: 每30秒或500条
    状态打印: 每5分钟
    健康检查: 每30秒, 60秒无数据触发重连
    结算检查: 每秒
    结算超时: 5分钟无数据 → 超时结算
    启动清理: 4小时前待结算 → 标记超时

12.2 盈亏参数
    WIN_PROFIT_USD  = +4.0 U
    LOSE_PROFIT_USD = -5.0 U
    超时等同亏损: -5.0 U

12.3 策略参数
    趋势过滤窗口: 5分钟
    v1 趋势阈值: 0.2% (0.002)
    v2 趋势阈值: 0.5% (0.005)
    冷却间隔: 1分钟
    20分钟窗口极值间隙: 3分钟
    其他窗口极值间隙: 1分钟

12.4 数据写入参数
    批量写入阈值: 500条
    写入去重TTL: 30分钟

12.5 WebSocket参数
    连接地址: wss://data-stream.binance.vision/ws/ethusdt@kline_1s
    连接超时: 30秒
    重连延迟: 5秒 (OnClose/OnError), 3秒 (健康检查)
    会话空闲超时: 0 (不超时)
